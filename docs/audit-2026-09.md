## Q1 — What toke version does ooke actually require?

**Answer: `mintoke = "2.8.0"`, and that answer is not precise enough to be useful. Fixing
that imprecision is part of 134.7.**

`ooke.toml` declares `2.0.0`. That is wrong by a wide margin. The source uses language
features that a 2.0.0 compiler would reject outright:

| Feature | Landed | Usage in `src/` |
|---|---|---|
| `=` assignment / `==` equality split (v0.4, Epic 116 / A3) | post-2.8.0 | 120 `==` occurrences; a 2.0.0 compiler treats `=` as equality and rejects these |
| `@(...)` array and map literals; `[]` removed (Epic 116 syntax decision) | post-2.8.0 | 153 occurrences |
| `mut.` mutable bindings | post-2.8.0 | 58 occurrences |
| `T!$err` error unions with `!` propagation and `mt` arms | 2.x | 64 `!$…` propagations |
| `if`/`el` as an expression (116.1/A1) | post-2.8.0 | used in `template.tk`, `cli.tk` |
| Escape-by-default template engine (ADR-0011, ooke 124.3) | post-2.8.0 | `src/template.tk` depends on the stdlib html-escape surface |
| Capability model (ADR-0010, 124.4e) | post-2.8.0 | the compiled binary is subject to `CAP001` |
| `std.queue`, `std.set`, `std.stack` (collections) | 2.6.0 | imported by `src/` |
| `std.db`, `std.md`, `std.toml`, `std.process`, `std.args` | ≤2.8.0 | imported by `src/` |

Full stdlib import set used by `src/`:
`std.args std.db std.file std.http std.json std.log std.md std.path std.process std.queue
std.set std.stack std.str std.toml`.

**The complication.** `toke/VERSION` has read `2.8.0` since commit `f1e30b3` (story 113.B).
Everything since — the whole of Epics 114 through 134, including the v0.4 syntax break,
ADR-0010 capabilities, ADR-0011 escaping, the lint rules and the pattern catalogue — shipped
under that same version string. So `2.8.0` is simultaneously the version that *cannot*
compile ooke (pre-v0.4 2.8.0) and the version that can (today's 2.8.0). A `mintoke` semver
floor is therefore unenforceable today.

**Recommendation for 134.7:**
1. Set `ooke.toml [requires] mintoke = "2.8.0"` now — it is the only defensible value.
2. Raise the real problem upstream: toke must bump `VERSION` for the v0.4 syntax break.
   Until it does, add a second, *enforceable* floor to `ooke.toml` — a minimum toke commit
   or build date — and make `Makefile: check-toke-version` a prerequisite of `all`
   (it is currently defined but never run, so the existing gate is dead code).
3. `MIN_TOKE_VERSION := 2.0.0` in the `Makefile` must move in lockstep with `ooke.toml`;
   today the two agree only because both are wrong.

## Q2 — Are the 19 standalone `--check` failures a tooling gap or real defects?

**Answer: 18 of 19 are a pure include-path gap, fixed by one flag. 1 is genuinely broken
source.** ooke *can* be linted, measured and gated, starting today.

The 19 failures reproduce exactly as reported:

```
$ cd ~/tk/toke-ooke
$ for f in $(find . -name '*.tk' -not -path './.git/*'); do tkc --check "$f" >/dev/null 2>&1 || echo "FAIL $f"; done
# → 19 failures out of 30
```

The cause is that ooke's `.tki` interfaces live in `src/` (`src/ooke.config.tki`,
`src/ooke.router.tki`, …) and `tkc` resolves `.tki` relative to the **current working
directory** unless told otherwise. The Makefile hides this by doing `cd $(SRC) && $(TKC) …`
on every rule, so the interfaces resolve implicitly. Any invocation from the repo root —
which is how a human, a linter or CI would do it — cannot see them.

**The invocation that makes them check cleanly** (`-I` adds a `.tki` search directory;
`TKC_INTERFACE_PATH=src` is the environment equivalent):

```
$ tkc --check -I src <file>
```

Result over all 30 files:

```
$ ./scripts/audit_tk.sh check
# → 29 passed, 1 failed
```

**(b) Genuinely broken source — 1 file.**

`testproj/pages/api/hello.tk` fails *with* `-I src`:

```
error[E2002]: expected field, got '$'   at testproj/pages/api/hello.tk:5:9
error[E2003]: missing semicolon         at testproj/pages/api/hello.tk:5:9
  5 |   <http.$res{status:200;body:req.body;headers:@()};
```

A qualified struct *literal* (`<module>.$<type>{…}`) is not accepted in expression position
by the current parser. A qualified struct *type* is fine — the same file's signature
`f=post(req:http.$req):http.$res` parses, and `testproj/pages/index.tk` compiles because it
returns `tpl.renderfile(…)` rather than constructing an `http.$res` inline. 134.2 must decide
whether to add parser support or rewrite the handler to build the response another way.
Note that `testproj/` is the scaffold a user gets from `ooke new` — a broken scaffold is a
user-facing defect, not a test fixture.

### Why this went unnoticed — the gates are decorative

Both existing Makefile gates are incapable of failing on this class of problem:

- `make check` (Makefile:212–219) pipes through `head -5` and ends with `|| true`. It can
  never exit non-zero. It also covers only 12 of the 16 `src/`+`pages/` files — it omits
  `src/_handlers.tk`, `pages/*.tk` and all of `testproj/`.
- `make test-check` (Makefile:222–230) counts only diagnostics that are
  `"severity":"error"` **and** `"stage":"parse"` **and** `grep -v 'E2030'`. It explicitly
  filters out the very errors this question is about, and silently ignores every
  name-resolution, type and codegen error.
- CI (`.github/workflows/ci.yml`) runs `make test-check || echo "test-check completed with
  warnings"`, so even a genuine failure cannot fail the job. CI also triggers only on
  `main`, and the repo's current HEAD is on `feature/ooke-124.4e-capability-manifest`,
  which has never been CI-verified.

**134.2 must therefore do three things:** add `-I src` (or `TKC_INTERFACE_PATH`) to a real
`check` target that covers all 30 files, delete the `|| true` / `head -5` / `grep -v E2030`
suppressions, and fix `testproj/pages/api/hello.tk`.

## Q3 — What v0.3-era residue remains?

**Answer: 7 `:void` returns in 4 files. That is the entire residue.** No removed syntax, no
old stdlib call names, and the three `@($type)` sites the migrator flags turn out to be
correct v0.4 — the migrator is wrong, not ooke.

Method: `tkc --migrate` was run over all 30 files and diffed against the source, which shows
exactly what the v0.4 migrator would rewrite; supplemented by targeted greps.

### `:void` returns — W1020, 7 occurrences

| File:line | Function |
|---|---|
| `src/build.tk:25` | `buildpage(...):void!$builderr` |
| `src/cli.tk:11` | `cliprintusage():void` |
| `src/cli.tk:30` | `cliprintversion():void` |
| `src/serve.tk:13` | `servegetjson(pattern;json):void` |
| `src/serve.tk:18` | `servepostjson(pattern;json):void` |
| `src/serve.tk:23` | `serveregisterstatic(...):void` |
| `src/validate.tk:107` | `validatelogresult(result:$valresult):void` |

**None of the seven bodies ends in a `<` return statement**, so 134.2 is 7 signature edits
*and* 7 `<0` insertions. The diagnostic's own `fix` field says as much ("replace 'void' with
'i64' and add '<0' as last statement") but `tkc --migrate` only performs the first half.

### `@($type)` — investigated, and it is **not** residue

`tkc --migrate` proposes rewriting three sites from `@($T)` to `@$T`:

| File:line | Text |
|---|---|
| `src/build.tk:185` | `$modeldef{name:"";fields:@($fielddef)}` |
| `src/template.tk:412` | `<$tplcache{entries:@($str:@($token))}` |
| `src/validate.tk:131` | `$valresult{errors:@($valerror);warnings:@($valerror)}` |

**Those three are correct as written and must not be changed.** `@($T)` is the required
spelling for an empty typed-array *value*; the bare `@$T` form is legal only inside a `t=`
type declaration. Applying the migrator's suggestion produces
`error[E2002]: expected '(' after '@', got '$'`. ooke already gets this distinction right
throughout — `src/validate.tk:21` declares `fields:@$fielddef` in the type and
`src/validate.tk:46` writes `mut.@($fielddef)` in the expression — and there are ~30 other
`@($…)` expression sites (`store.tk`, `router.tk`, `main.tk`, `_handlers.tk`) that the
migrator correctly leaves alone.

The migrator flags exactly these three because they sit in struct-literal *field-initialiser*
position with a user-defined element type, which it misreads as a type declaration. **This is
a compiler defect to file, not ooke work.**

> **Do not run `tkc --migrate` over ooke.** Two migrator defects make it unsafe:
> 1. the `@($T)` → `@$T` rewrite above, which does not parse;
> 2. it **deletes block comments** — `src/cli.tk:44–47`, a four-line `(* … *)` comment
>    explaining the Coin Gold placeholder theme, is replaced with whitespace.
>
> 134.2 should apply the 7 `:void` conversions by hand.

### Checked and clean

- **Removed `[]` array syntax** — every `[` in the repo is inside a string literal (TOML
  section headers in test fixtures, and `[slug]`/`[section]` route *filenames*). No residue.
- **Old stdlib call names / underscore identifiers** — every underscore match is inside a
  string literal (`/tmp/test_ooke.toml` and friends). All call-names already conform to the
  no-underscore convention (113.2a). Filenames `test_*.tk` and `src/_handlers.tk` retain
  underscores but those are paths, not identifiers.
- **`=` vs `==`** — all 120 comparison sites already use `==` (migrated in commit `54e3d64`).
- **`<!$err{…}` dead raises** — 0 occurrences; cleaned up in `d34bc5a` (113.10a).

## Q6 — Is the build reproducible from a clean clone?

**Answer: yes on this machine, byte-for-byte; no on any other machine without overrides.**

`git clone ~/tk/toke-ooke /tmp/ooke-clean-134 && make` succeeds in ~10 s with exit 0 on both
`main` and the feature branch, producing `ooke-toke` at 879,864 bytes,
sha256 `087f6d97e84357bd6f077d2e39d714259ca2073e055d65d1d9b320a9ad725774` — identical to the
committed working-tree binary. `git status` in the clone is clean afterwards, so every build
output is correctly gitignored.

**No required file is missing from git.** `src/_handlers.tk` is both committed *and*
regenerable from `pages/` (verified by forcing the rule). The 13 committed `src/ooke.*.tki`
are published contracts, whitelisted by `!src/ooke.*.tki`; the build reads the generated
`src/ooke/*.tki` instead. The only stray is `config.ll` at the repo root, which nothing
produces or consumes.

**Host-specific assumptions in the Makefile** (all `:=`, so command-line-overridable):

1. `TKC := /Users/matthew.watt/tk/toke/toke` — absolute path to a pre-built compiler.
2. `TOKE_ROOT := /Users/matthew.watt/tk/toke` — absolute path to a sibling toke checkout.
3. `TOKE_STDLIB` — **57 named `.c` files plus 18 `*_glue.c` files enumerated by hand.** Any
   upstream rename or removal breaks the link. This is what commit `0bb5dc1` ("drop
   security.c from stdlib link set — removed upstream") was repairing. The most brittle
   part of the build.
4. `TOKE_VENDOR` — `cmark/src/*.c` and `tomlc99/toml.c`.
5. `clang` on PATH; `LIBS := -lssl -lcrypto -lz -lm -lsqlite3`.
6. The Darwin branch hardcodes Apple-Silicon Homebrew prefixes (`/opt/homebrew/{include,lib}`);
   Intel macOS (`/usr/local`) would not be found. (`release.yml` gets this right with
   `brew --prefix`; the Makefile does not.)
7. `check-toke-version` is defined but is **not a prerequisite of `all`**, so the version
   gate never runs.

With a bad root the failure is immediate and legible:
`make TKC=/nonexistent/toke → /bin/sh: /nonexistent/toke: No such file or directory`.

**CI** (`.github/workflows/ci.yml`) already works around every hardcoded path — it clones
`karwalski/toke` `main`, builds it, and passes `TKC`/`TOKE_ROOT`/`TOKE_STDLIB`/`TOKE_VENDOR`
explicitly. Two gaps: it pins nothing about the compiler (always `main`, so an upstream
stdlib change breaks ooke silently — exactly the Q1 drift problem), and it runs only on
`main`, so the current HEAD branch has never been verified. `release.yml` is a proper 4-way
matrix release job with checksums.

**Makefile nit:** the multi-output rules (`$(IFACE_DIR)/build.tki $(IFACE_DIR)/build: …`)
are not GNU grouped targets (`&:`), so make runs the recipe twice for `build`, `serve`,
`handlers` and `cli`. Harmless (the compiler is deterministic — hence the identical binary)
but it doubles that phase.

## Q7 — Does `ooke build` reproduce the website's `/docs/` pages?

**Answer: no. It aborts with `RT005: nil dereference` after 11 of ~120 pages. The root
cause is a toke compiler codegen bug, not an ooke logic error — and behind it sits a second
crash and a structural routing limitation. All three must be cleared for 134.8.**

### Reproduction

```
$ cp -R ~/tk/toke-website /tmp/ooke134-web && cd /tmp/ooke134-web && rm -rf build && mkdir build
$ ~/tk/toke-ooke/ooke-toke build
RT005: nil dereference          # on stderr
$ echo $?
1
$ find build -name '*.html' | wc -l
11
```

`sitemap.xml` lists **120** URLs. 11 are produced. Everything under `/docs/<section>/<slug>`
is missing — this is exactly the 132.20 blocker.

### Diagnosis — the exact failing input and runtime state

An instrumented copy of `src/build.tk` (in `/tmp/ooke134-src`, never committed) localises
the trap to `src/build.tk:183–184`, inside `buildrun`'s dynamic-route loop:

```toke
let model=mt validate.validateloadmodel(modelsdir;ctype) {$ok:m m;$err:e $modeldef{name:"";fields:@($fielddef)}};
let hasmodel=model.fields.len>0;     // ← RT005 fires here
```

Runtime state at the trap:

- route `j` = `/docs/learn/:slug`, `isdynamic` = true
- `ctype` = `"docs/learn"`
- `store.storeall(contentdir;"docs/learn";"flat")` succeeded, `col.len` = 17
- `modelsdir` = `<project>/models`, **which does not exist** on the toke website
- so `validate.validateloadmodel` fails at its first statement
  (`file.read(tomlpath)!$validateerr`, `validate.tk:33`)
- the `mt` should bind `model` to the `$err` arm's `$modeldef{name:"";fields:@($fielddef)}`
- it does not. `model` holds the `$validateerr` payload pointer instead
- reading `.fields` off that base hits a null and `tk_nil_trap` fires `RT005`

### Root cause — `mt` never takes the `$err` arm for a user-defined toke function

This is a **toke compiler codegen defect**, reproducible in 15 lines with no ooke involved:

```toke
m=main;
i=log:std.log;
i=str:std.str;
t=$verr{msg:$str};
f=fails(x:i64):i64!$verr{
  if(x>0){ <$err($verr{msg:"boom"}) }el{};
  <42
};
f=main():i64{
  let a=mt fails(1) {$ok:v str.concat("OK:";str.fromint(v));$err:e str.concat("ERR:";e.msg)};
  (log.info(str.concat("mt fails(1) -> ";a);@()));   // → "OK:4336856880"  (expected "ERR:boom")
  let c=mt fails(1) {$ok:v 100;$err:e 200};
  (log.info(str.concat("consts -> ";str.fromint(c));@()));  // → 100        (expected 200)
  <0
};
```

Established by experiment:

- The `$err` arm is **never** selected for a call to a user-defined toke function. The error
  discriminant is not read; `mt` always takes `$ok` and binds the raw returned word — which,
  on the failure path, is the error payload pointer.
- Identical at `-O0`, `-O1`, `-O2` and `-O3`, so it is not an optimiser artefact.
- `!` propagation out of a user-defined function is broken the same way:
  `f=prop(x):i64!$verr{ let v=fails(x)!$verr; <v+1000 }` returns `payload+1000` on the
  failure path instead of propagating.
- **`mt` over a *stdlib* call is correct.** `mt file.write("/nonexistent/x";"y")
  {$ok:v true;$err:e false}` correctly yields `false`; `mt file.read(<missing>)
  {$ok:v v;$err:e "FALLBACK"}` correctly yields `"FALLBACK"`. The defect is specific to
  toke-level `T!$err` returns.
- `docs/known-limitations.md:159` claims the opposite — "Verified 2026-07-01:
  `let r=mt st.toint(x){$ok:v v; $err:e <0}` returns `0` on the error arm." That
  verification no longer holds; the same shape now returns garbage. The doc needs correcting
  and the regression needs bisecting.

**Blast radius.** The idiom is everywhere. In `src/` alone: 13 `mt` sites over ooke-module
functions (`tpl.tplrenderfile` ×5, `store.storeall` ×2, `config.configload` ×2,
`validate.validateloadmodel`, `serve.serverun`, `router.routerscan`, `build.buildrun`) and
53 `!$<ookeerror>` propagations. The dominant spelling `{$ok:v true;$err:e false}` returns
**`true` on failure**, so ooke currently treats a large class of failures as successes
*silently*; the RT005 is merely the first case where the corrupted value is dereferenced.
This is a P0 compiler defect that belongs in its own story — it is not fixable inside
`toke-ooke`, which is bound by ADR-0005 to use the stdlib rather than work around it.

### Second crash, behind the first

Bypassing the `validateloadmodel` read on a throwaway copy moves the build forward through
all 17 `/docs/learn/:slug` pages (28 HTML files) and then **segfaults (exit 139)** on the
next dynamic route:

```
DBG loop j pattern=/docs/:section/:slug
DBG ctype=docs/[section]
DBG storeall ok
<SIGSEGV>          # crashes evaluating col.len at src/build.tk:182
```

Same mechanism: `store.storeall(contentdir;"docs/[section]";"flat")` fails because
`content/docs/[section]` is not a real directory, the `$err:e @()` arm is not taken, `col`
holds the error payload, and `col.len` dereferences it.

### Third problem — structural, and not a compiler bug

Even with both crashes fixed, `pages/docs/[section]/[slug].tk` **can never build**:

- `buildrun` derives `ctype` from the route path, giving the literal `"docs/[section]"`,
  and looks for a content directory of that name.
- `buildoutputpath` only ever substitutes `:slug`
  (`str.replace(routes.get(j).pattern;":slug";slug)`, `src/build.tk:203`). A second dynamic
  segment has no substitution at all.

So ooke's static build supports exactly **one** dynamic segment, named `:slug`, backed by a
literal content directory. That is the other half of 132.20 and it is real ooke work:
either generalise the dynamic-segment expansion (cartesian over `content/docs/*/*`), or
generate the docs tree statically.

### One more reproducibility trap for 134.8

`toke-website/content/docs/*` are twelve **absolute symlinks** into
`/Users/matthew.watt/tk/toke/docs` (`about`, `community`, `compiler`, `cookbook`,
`decisions`, `examples`, `getting-started`, `learn`, `reference`, `spec`, `stdlib`,
`tutorials`), created 2026-09-19 13:15. The docs content is not in the website repo at all.
Any reproducible build must resolve that dependency explicitly (a make step that materialises
or vendors the docs) rather than relying on one developer's home directory.

### Sizing judgement

**134.2 is small and mechanical: roughly half a day.** 18 of the 19 `--check` failures
vanish with one `-I src` flag; the real content is 7 `:void` conversions (14 edits), 3
`@($T)` spellings, one broken scaffold file, and rewriting three Makefile/CI targets so they
can actually fail. The risk is not volume — it is that `tkc --migrate` (D17) must **not** be
used, so the edits are manual and need the tests from 134.5 behind them.

**134.3 is much larger than the "15 lint hits" headline suggests — it is the biggest story
in the epic.** The lint number to clear is 100 warnings, but the real unit is rewrite sites:
**319 in `src/`, ~488 across the repo.** ooke predates Epic 131 completely — zero
interpolation, zero `el if`, zero `br`, zero `s.builder`, zero `.map`/`.filter` — so this is
not a tidy-up, it is a dialect migration of 13 modules.

Three things make it harder than the count alone implies:

1. **Only 64% is machine-findable.** `tkc --lint` covers 203 of the 319 src sites. The
   remaining 116 — including all 53 nested-`if` sites, the single biggest category after
   concat and single-use-let — have no lint rule at all (D21f) and must be found by reading.
2. **One file is a third of the work.** `src/cli.tk` is ~103 sites, and 41 of its concat
   lines are nested. Clearing it is a rewrite of that module's string handling.
3. **The story demands "behaviour identical, proven by ooke's own tests"** — and ooke has no
   executed tests at all (D6). So 134.3 is genuinely blocked on 134.5, not merely on 134.2,
   and 134.5 in turn is blocked on D1. Attempting 134.3 before then would produce an
   unverifiable claim.

Realistic shape: one pass per pattern family across all 13 modules, concat→interpolation
first (so the 33-site overlap with `single-use-let` collapses), `cli.tk` as its own
increment, and the 11 letter-only sites (D4's excluded three patterns) explicitly declared
out of scope. Budget several days of focused work, not an afternoon — and take the proxy8k
baseline (14,368) before the first edit so 134.4 has a before number.

**Both are gated by D1.** Until `mt`'s `$err` arm works for toke-level functions, no ooke
test can distinguish a pass from a silent failure, and any "behaviour identical, proven by
ooke's own tests" claim in 134.3 would be unfounded.
